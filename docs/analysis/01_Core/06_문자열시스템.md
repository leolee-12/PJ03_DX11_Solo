## 쉬운 개념 가이드

**왜 문자열 타입이 3개나 필요한가?**
- 게임에서 문자열은 용도가 다양하다: 이름 비교, 텍스트 조작, UI 표시
- 용도마다 최적화 방향이 다르므로 3가지로 나눔

| 타입 | 용도 | 비유 |
|------|------|------|
| **FString** | 자유롭게 수정 가능한 문자열 | 연필로 쓴 메모 (지우고 다시 쓸 수 있음) |
| **FName** | 변경 불가 식별자, 비교가 초고속 | 학생 번호 (이름 대신 번호로 비교 → 즉시) |
| **FText** | 화면에 보여주는 텍스트, 다국어 지원 | 번역된 UI 텍스트 ("게임 시작" / "Start Game") |

**이 문서의 핵심 주제 — FName:**
| 용어 | 쉬운 설명 |
|------|----------|
| 해시 테이블 | "이름 → 번호" 변환표. "Weapon"을 넣으면 고유 번호 12345를 돌려줌 |
| 샤드(Shard) | 큰 테이블을 여러 조각으로 나눈 것. 여러 스레드가 각자 다른 조각을 쓰면 충돌 감소 |
| 리니어 프로빙 | 자리가 차있으면 바로 옆 자리를 확인하는 방식 |
| 로드 팩터 | 테이블이 얼마나 찼는지 비율. 90% 차면 테이블 크기를 2배로 늘림 |
| Bump Allocator | 메모리를 한 방향으로만 쌓아가는 할당자. 빠르지만 중간에 해제 불가 |
| CityHash64 | Google이 만든 빠른 해시 함수. 문자열 → 64비트 숫자 변환 |

## 1. FName 전역 해시 테이블 구조

### 전체 그림

> FName 시스템의 핵심 아이디어:
> 1. "Weapon"이라는 문자열이 처음 등장하면 **전역 테이블에 한 번 등록**하고 고유 번호(ID)를 받음
> 2. 이후 "Weapon"이 또 나오면 새로 등록하지 않고 **같은 번호를 재사용**
> 3. 비교 시 문자열을 한 글자씩 비교하는 대신 **번호끼리 비교** → O(1)

```
FNamePool (전역 싱글톤 — 프로세스에 딱 1개)
├── FNameEntryAllocator         ← 문자열 원본 저장소 (페이지 블록)
├── ComparisonShards[256]       ← 해시 테이블 (대소문자 무시 비교용)
└── DisplayShards[1024]         ← 해시 테이블 (에디터에서 대소문자 보존용)
```

### FNameEntryAllocator — 문자열 저장소

> 비유: 끝없이 이어지는 노트. 새 이름이 들어오면 노트 끝에 적고, 지우개는 없음.

```
블록 구조:
  Blocks[0]: [Weapon][Shield][Potion][...]  ← 첫 번째 블록
  Blocks[1]: [Enemy][Boss][...]             ← 두 번째 블록 (첫 블록이 다 차면)
  ...
  최대 8192 블록 (약 1~2GB)
```

- **해제 불가**: 한 번 등록된 문자열은 프로세스 종료까지 남아있음
- FNameEntryId = `블록번호 × 65536 + 오프셋` → uint32 하나로 위치 표현

### FNamePoolShard — 해시 테이블 조각

> 비유: 전화번호부를 "ㄱ", "ㄴ", "ㄷ"... 등 자음별로 나눈 것.
> 여러 사람(스레드)이 동시에 다른 자음 페이지를 써도 충돌 안 남.

- **샤드 수**: 256개 (런타임) / 1024개 (에디터)
- **해시 함수**: CityHash64 → 상위 비트로 샤드 선택, 하위 비트로 슬롯 위치
- **충돌 처리**: 리니어 프로빙 (자리가 차있으면 바로 옆 확인)
- **로드 팩터**: 90% 차면 2배 확장
- **동시성**: 샤드별 읽기/쓰기 잠금 (RWLock)

### FNameSlot — 슬롯 하나의 구조

```cpp
struct FNameSlot {
    uint32 IdAndHash;  // 하위 29비트 = 문자열 ID, 상위 3비트 = 해시 일부
};
// 단 4바이트! — 캐시 효율적
```

> 상위 3비트 해시: 슬롯을 확인할 때 문자열 원본까지 가지 않고 이 3비트만으로 "아, 이건 내가 찾는 게 아니네"를 빠르게 판별

## 2. FName 생성 시 문자열 등록 흐름

### 전체 흐름 (FName("Weapon_3") 생성 시)

```
1. 문자열 파싱: "Weapon_3" → 이름부분="Weapon" + 번호=3
2. "Weapon"을 소문자로 변환 → CityHash64 해시 계산
3. 해시에서 샤드 번호 추출 → 해당 샤드의 해시 테이블 검색
4. 이미 있으면: 기존 ID 반환 (새로 저장 안 함)
5. 없으면: 문자열을 FNameEntryAllocator에 저장 → 새 ID 발급
6. FName 객체 = {ComparisonIndex=ID, Number=4}
   (Number 내부값 = 외부값+1, 즉 3+1=4)
```

### Number 파싱 규칙

> FName은 문자열 끝의 `_숫자` 부분을 자동으로 분리한다.

```
"Weapon_3"  → 이름="Weapon",  Number=3  ✓ 분리됨
"Weapon_03" → 이름="Weapon_03"          ✗ 선행 0이 있어서 분리 안 함
"Weapon"    → 이름="Weapon",  Number=없음
"Weapon_"   → 이름="Weapon_"            ✗ 숫자가 없어서 분리 안 함
"123"       → 이름="123"               ✗ _가 없어서 분리 안 함
```

**왜 이렇게 하나?** "Weapon_0", "Weapon_1", "Weapon_2"처럼 같은 이름의 복제본을 구분하기 위해.
문자열 부분("Weapon")은 테이블에 한 번만 저장하고, 번호만 다르게 하면 메모리 절약.

## 3. FName 비교가 O(1)인 이유

### FName의 내부 구조

```cpp
class FName {
    FNameEntryId ComparisonIndex;    // uint32 — 전역 테이블의 ID
    uint32 Number;                   // 인스턴스 번호
};
// sizeof(FName) = 8바이트 (런타임)
```

### operator== (비교 연산)

```cpp
bool operator==(FName Other) const {
    // 64비트 플랫폼: 8바이트를 통째로 비교!
    return ToComparableInt() == Other.ToComparableInt();
}
```

> **핵심**: 동일 문자열은 전역 테이블에서 동일한 ID를 받으므로,
> **숫자 비교 한 번 = 문자열 동일성 판별**. CPU 명령어 1~2개로 끝남.

**비교:**
- `FString("Weapon") == FString("Weapon")` → 한 글자씩 비교 → O(N)
- `FName("Weapon") == FName("Weapon")` → 숫자 비교 → O(1)

## 4. FString ↔ FName ↔ FText 변환 비용

> 변환할 때마다 비용이 발생하므로, 처음부터 적절한 타입을 선택하는 것이 중요.

| 변환 | 방법 | 비용 | 왜? |
|------|------|------|-----|
| FString → FName | `FName(Str)` | **높음** | 해시 계산 + 테이블 검색/등록 |
| FName → FString | `Name.ToString()` | 중간 | 테이블에서 문자열 복사 + 힙 할당 |
| FString → FText | `FText::FromString(Str)` | 낮음 | 그냥 감싸기만 함 |
| FText → FString | `Text.ToString()` | 낮음 | 내부 문자열 참조 반환 |
| FName → FText | `FText::FromName(Name)` | 중간 | FName→FString→FText 2단계 |
| FText → FName | 직접 함수 없음 | **높음** | FText→FString→FName |

**팁**: 비교가 잦은 식별자는 FName, UI 표시는 FText, 문자열 조작은 FString.

## 5. FName의 Number 필드

### 역할 — 같은 이름의 복제본 구분

```
에디터에서 적(Enemy) 액터를 3번 복제하면:
  Enemy    → FName("Enemy", 번호 없음)
  Enemy_0  → FName("Enemy", 0)  → 내부 Number=1
  Enemy_1  → FName("Enemy", 1)  → 내부 Number=2
```

- 모두 같은 ComparisonIndex("Enemy"의 ID)를 공유 → 문자열 1번만 저장
- Number 값만 달라서 구분

### 왜 내부값 = 외부값 + 1인가?

```cpp
#define NAME_NO_NUMBER_INTERNAL 0   // 번호 없음 = 내부값 0
```

- `memset(0)`으로 초기화하면 자동으로 "번호 없음" 상태가 됨
- 프로그래밍에서 0 초기화는 가장 흔한 패턴이므로, 안전한 기본값

## 6. FName 메모리 특성

### sizeof(FName)

| 빌드 | 크기 | 구성 |
|------|------|------|
| 런타임 | **8바이트** | ComparisonIndex(4) + Number(4) |
| 에디터 | **12바이트** | + DisplayIndex(4) |

### 메모리 회수 불가 ★주의★

```
소스 코드 주석:
"FName strings are never freed and should be created sparingly."
(FName 문자열은 절대 해제되지 않으며 아껴서 만들어야 합니다.)
```

- Bump Allocator 방식 — 앞으로만 쌓고, 중간 해제 불가
- **매 프레임 고유한 FName을 만들면 메모리가 계속 증가** (사실상 메모리 누수)
- 해결: 반복적으로 사용되는 고정 이름만 FName으로, 동적 문자열은 FString으로

## 7. 프레임워크 적용 — 해시 기반 식별자 설계 가이드

### 두 가지 단순화 방안

**옵션 A: 해시만 사용 (테이블 없음)**
```cpp
constexpr uint32 ID_Idle   = CompileTimeHash("Idle");
constexpr uint32 ID_Attack = CompileTimeHash("Attack");

uint32 currentState = ID_Idle;
if (currentState == ID_Attack) { ... }  // 숫자 비교 = O(1)
```
- 장점: 메모리 최소, 초고속, 구현 단순
- 단점: 원본 문자열 복원 불가, 해시 충돌 가능 (극히 드묾)
- 적합: 내부 식별자 (AI 상태, 이벤트 이름 등)

**옵션 B: 전역 테이블 (UE4 간소화)**
- `unordered_map<uint32, string>` 전역 테이블
- 장점: 디버깅 시 원본 문자열 확인 가능
- 단점: 메모리 해제 정책 결정 필요
- 적합: 에셋/오브젝트 이름 (사용자에게 표시되는 것)

### 설계 시 핵심 주의사항

1. **컴파일 타임 해시**: constexpr로 리터럴 문자열을 컴파일 시점에 변환 → 런타임 비용 0
2. **Number 필드**: 복제본 구분이 불필요하면 생략 (8바이트 → 4바이트)
3. **대소문자**: 내부 식별자는 대소문자 무시가 안전 (UE4와 동일)
4. **메모리**: 수천 개 이하 고유 이름이면 해제 불가도 무방
5. **디버그**: 해시→문자열 역방향 테이블은 디버그 빌드에서만 유지
