## 쉬운 개념 가이드

**메모리 관리란?**
- 프로그램이 실행되려면 데이터를 저장할 공간(메모리)이 필요하다
- C++에서는 `new`로 메모리를 빌리고 `delete`로 반납한다
- 문제: 반납을 깜빡하면 **메모리 누수**(계속 빌리기만 해서 공간 부족), 이미 반납한 걸 또 쓰면 **크래시**
- UE4는 이런 문제를 줄이기 위해 **메모리 할당자**와 **스마트 포인터**를 자체 구현했다

**핵심 비유:**
| 개념 | 비유 |
|------|------|
| 메모리 할당자(FMalloc) | 도서관 사서 — 책(메모리)을 빌려주고 반납받는 사람 |
| 풀(Pool) 할당 | 사서가 미리 크기별로 책꽂이를 만들어둠 → 요청 시 바로 꽂이에서 꺼내줌 (빠름) |
| TLS 캐시 | 각 열람실(스레드)마다 자주 쓰는 책을 미리 갖다놓음 → 사서에게 안 가도 됨 |
| 프록시 할당자 | 기존 사서를 감싸서 기능 추가 (예: 반납 기록 남기기, 훼손 감지) |
| 스마트 포인터 | 자동 반납 시스템이 달린 대출증 — 모두 반납하면 책 자동 폐기 |

## 1. FMalloc 계열 할당자 상속 구조

### 1.1 계층도

> `FMalloc`은 메모리 할당/해제의 인터페이스(규격)이고, 아래 클래스들이 각각 다른 전략으로 구현한다.

```
FUseSystemMallocForNew           ← 할당자 자신은 시스템 malloc으로 생성 (순환 방지)
└── FMalloc : FUseSystemMallocForNew, FExec   ← 할당자 인터페이스 (추상 클래스)
    │
    ├── [실사용 할당자 — 실제로 게임에서 메모리를 관리하는 것들]
    │   ├── FMallocAnsi (final)       ← C 표준 malloc 그대로 사용 (가장 단순)
    │   ├── FMallocBinned             ← 1세대: 크기별 풀(바구니)로 관리
    │   ├── FMallocBinned2            ← 2세대: 개선된 풀 + 스레드별 캐시 ★기본값★
    │   ├── FMallocBinned3            ← 3세대: 가상 메모리 기반 (64bit 전용)
    │   ├── FMallocTBB (final)        ← Intel TBB 라이브러리 활용
    │   ├── FMallocJemalloc           ← jemalloc 활용 (Linux/FreeBSD)
    │   └── FMallocMimalloc (final)   ← mimalloc 활용 (Microsoft 제작)
    │
    ├── [디버그/진단 할당자 — 버그 찾기용]
    │   ├── FMallocStomp (final)      ← 메모리 경계 침범 시 즉시 크래시로 알려줌
    │   └── FMallocDebug              ← 메모리 앞뒤에 표식을 달아 침범 감지
    │
    └── [프록시 할당자 — 기존 할당자를 감싸서 기능 추가]
        ├── FMallocThreadSafeProxy    ← 멀티스레드 안전 잠금 추가
        ├── FMallocPoisonProxy        ← 해제된 메모리를 0xcd로 채움 (재사용 감지)
        ├── FMallocDoubleFreeFinder   ← 같은 메모리를 두 번 해제하는 버그 감지
        ├── FMallocReplayProxy        ← 할당 이력 기록/재생 (프로파일링)
        ├── FMallocFrameProfiler      ← 매 프레임 할당 통계
        └── FMallocTimer              ← 할당 소요 시간 측정
```

### 1.2 할당자별 특성 요약

| 할당자 | 전략 | 언제 쓰나? |
|--------|------|-----------|
| `FMallocAnsi` | C malloc 직접 사용 | 디버깅/폴백 (가장 단순하지만 느림) |
| `FMallocBinned2` | 크기별 45개 바구니 + 스레드 캐시 | **기본 할당자** — 빠르고 단편화 적음 |
| `FMallocStomp` | 보호 페이지 | 메모리 침범 버그 찾을 때 |
| `FMallocPoisonProxy` | 해제 메모리 오염 | "이미 반납한 메모리를 쓰는" 버그 찾을 때 |

### 1.3 FMallocBinned2 세부 구조

> **왜 풀(Pool) 방식을 쓰나?**
> 매번 OS에 메모리를 요청하면 느리다. 미리 큰 덩어리를 받아놓고 잘라서 나눠주면 훨씬 빠르다.
> 크기별로 바구니(풀)를 만들어두면, 16바이트 요청 → 16바이트 바구니에서 꺼내줌 → O(1) 속도.

```
FMallocBinned2
├── SmallPoolTable[45]            ← 크기별 45개 바구니 (8, 16, 32, ... ~32KB)
│   ├── ActivePools (FPoolList)   ← 아직 빈자리 있는 바구니들
│   └── ExhaustedPools            ← 다 찬 바구니들
│
├── FFreeBlock                    ← 빈 블록 하나
│   ├── Canary = 0xe3             ← 무결성 확인 표식 ("이 블록 정상이에요" 도장)
│   └── NextFreeBlock             ← 다음 빈 블록을 가리키는 포인터 (연결 리스트)
│
├── TLS 스레드별 캐시             ← 각 스레드가 자주 쓰는 블록을 미리 가져놓음
│   └── 번들(Bundle) 단위로 관리 (64KB)
│
└── 할당 크기 분류:
    ├── Small: ≤ 32752 바이트 → 45개 풀 중 맞는 크기에서 할당 (빠름)
    └── Large: > 32752 바이트 → OS에 직접 요청 (느리지만 큰 할당은 드물어서 OK)
```

**정렬 정책** (데이터 시작 주소를 깔끔한 배수로 맞추는 것 — CPU가 더 빠르게 읽을 수 있음):
- 16바이트 이상 블록: 16바이트 정렬
- 16바이트 미만 블록: 8바이트 정렬

## 2. 스마트 포인터 구현 방식

### 2.1 TSharedPtr / TSharedRef — 공유 소유권

> **문제**: A, B, C가 모두 같은 데이터를 사용 중인데, 누가 delete 해야 하나?
> **해결**: 참조 카운터로 "몇 명이 쓰고 있나" 세고, 0명이 되면 자동 삭제.

```
TSharedPtr<T, Mode>              ← nullptr 허용 (비어있을 수 있음)
TSharedRef<T, Mode>              ← nullptr 불허 (항상 유효한 객체를 가리킴)
├── ObjectType* Object            ← 실제 객체 포인터
└── FSharedReferencer<Mode>       ← 참조 카운터 래퍼
    └── FReferenceControllerBase* ← 제어 블록 (별도 힙 할당)
        ├── int32 SharedReferenceCount   ← 강참조 수 (이 숫자가 0이 되면 객체 파괴)
        ├── int32 WeakReferenceCount     ← 약참조 수 (이 숫자가 0이 되면 제어블록 파괴)
        └── virtual DestroyObject()      ← 객체 파괴 함수
```

**스레드 안전 모드 (ESPMode):**

| 모드 | 설명 | 비유 |
|------|------|------|
| `NotThreadSafe` | 카운터를 그냥 +1/-1 | 혼자 쓰는 계산기 |
| `ThreadSafe` | 원자적(Atomic) 연산으로 +1/-1 | 여러 사람이 동시에 눌러도 정확한 계산기 |

**참조 해제 흐름** (TSharedPtr이 소멸될 때):
```
TSharedPtr 소멸
  → 강참조 수 -1
  → 강참조 수가 0이 되면:
      → 객체(Object) 파괴 (DestroyObject)
      → 약참조 수 -1
      → 약참조 수도 0이면:
          → 제어 블록도 파괴 (모든 것 정리 완료)
```

### 2.2 TWeakPtr — 약한 참조

> **문제**: A가 B를 가리키고, B도 A를 가리키면? → 서로 참조 카운트가 0이 안 됨 (순환 참조)
> **해결**: 한쪽은 "약한 참조"(TWeakPtr)로 가리킴 → 카운트에 영향 안 줌.

```
TWeakPtr<T>
├── Object 포인터          ← 객체를 가리키지만, 이미 삭제됐을 수 있음
└── FWeakReferencer        ← 약참조 카운터 (제어 블록은 공유)
```

**사용법**: TWeakPtr을 쓰려면 먼저 `Pin()`으로 TSharedPtr로 변환해야 함:
```
Pin() 호출
  → 강참조 수가 0인지 확인
  → 0이 아니면: 강참조 수 +1 → TSharedPtr 반환 (안전하게 사용 가능)
  → 0이면: null 반환 (이미 삭제된 객체 → 사용 불가)
```

### 2.3 TUniquePtr — 단독 소유권

> 딱 1명만 소유할 수 있는 포인터. 복사 불가, 이동만 가능.

```
TUniquePtr<T, Deleter>
├── T* Ptr                  ← 소유 포인터
├── 복사 금지 (delete)       ← 다른 변수에 대입 불가
├── 이동만 허용 (MoveTemp)   ← 소유권을 넘길 수는 있음
└── 소멸 시 자동 delete
```

- 크기: 포인터 1개분 (8바이트) — 추가 오버헤드 없음
- **언제 쓰나?** 소유자가 확실히 1명일 때. 예: 컴포넌트가 자신만의 리소스를 관리할 때

### 2.4 MakeShared / MakeUnique

```cpp
// MakeShared: 객체 + 제어블록을 한 번에 할당 (메모리 1번 할당 = 빠름)
auto Ptr = MakeShared<Monster>(100); // HP가 100인 몬스터 생성

// MakeUnique: 단순히 new를 감싸서 TUniquePtr로 반환
auto Ptr = MakeUnique<Weapon>("Sword");
```

## 3. FMemory::Malloc() 호출 체인

> 코드에서 메모리를 요청하면 내부적으로 어떤 순서로 처리되는지.

```
사용자 코드: FMemory::Malloc(1024)   ← "1024바이트 빌려주세요"
  │
  └── GMalloc->Malloc(1024)          ← 현재 설정된 할당자가 처리
      (FMallocBinned2라면)
      → SmallPoolTable에서 1024바이트에 맞는 풀 찾기
      → TLS 캐시에 여유분 있으면 바로 반환 (잠금 없이!)
      → 없으면 풀에서 할당 (잠금 필요)
      → 포인터 반환
```

### 주요 함수

```cpp
// 핵심 3개 — 이것만 알면 됨
static void* FMemory::Malloc(SIZE_T Count, uint32 Alignment);   // 빌리기
static void* FMemory::Realloc(void* Original, SIZE_T Count);    // 크기 변경
static void  FMemory::Free(void* Original);                     // 반납

// 보조 함수
static void* FMemory::MallocZeroed(SIZE_T Count);               // 빌리고 0으로 초기화
static SIZE_T FMemory::GetAllocSize(void* Original);             // 실제 할당 크기 조회
```

## 4. 할당자 선택 및 교체

> 엔진 시작 시 커맨드라인으로 할당자를 바꿀 수 있다. 디버깅할 때 유용.

```
일반 실행:     → FMallocBinned2 (기본)
-ansimalloc    → FMallocAnsi (단순 malloc, 디버깅용)
-stompmalloc   → FMallocStomp (메모리 침범 감지)
-tbbmalloc     → FMallocTBB (멀티스레드 최적화)
```

- `GMalloc` — 전역 할당자 포인터 (프로세스에서 단 하나)
- 런타임 교체 불가, 시작 시 한 번 설정
- 할당자 자체는 시스템 malloc으로 생성 (자기 자신을 할당하는 모순 방지)

## 5. 프레임워크 관점 시사점

| UE4 패턴 | 프레임워크 적용 |
|----------|----------------|
| GMalloc 전역 싱글톤 + 가상 인터페이스 | 할당자 교체 가능한 구조 (디버그/릴리즈 분리) |
| FMallocBinned2의 풀 + TLS 캐시 | 소규모 엔진에서는 과도, mimalloc 래핑이 현실적 |
| FMallocThreadSafeProxy 프록시 패턴 | 기존 할당자에 기능을 비침투적으로 추가 |
| TSharedRef (비-nullable) | null 불가 참조로 API 안전성 강화 |
| MakeShared의 단일 할당 | 제어블록 + 객체를 한 번에 할당해 캐시 효율 향상 |
