## 쉬운 개념 가이드

**컨테이너란?**
- 데이터를 담는 "그릇". 어떤 그릇을 쓰느냐에 따라 데이터 넣기/찾기/삭제 속도가 달라진다

| 컨테이너 | 비유 | 특징 |
|----------|------|------|
| **TArray** (배열) | 번호순 사물함 | 순서가 있고, 끝에 추가는 빠르지만 중간 삽입/삭제는 느림 |
| **TMap** (맵) | 전화번호부 (이름→번호) | 이름(키)으로 번호(값)를 빠르게 찾음 |
| **TSet** (셋) | 출석부 | "있다/없다"만 빠르게 확인, 중복 불가 |

**자주 나오는 용어:**
| 용어 | 설명 |
|------|------|
| 해시(Hash) | 데이터를 숫자로 바꾸는 것. "홍길동" → 12345. 이 숫자로 빠르게 위치를 찾음 |
| 해시 충돌 | 다른 데이터가 같은 숫자를 받은 경우. "홍길동"과 "이몽룡"이 둘 다 12345가 될 수 있음 |
| 체이닝 | 충돌 시 같은 칸에 줄 세워두는 방법 |
| 슬랙(Slack) | 배열에 미리 확보해둔 여유 공간 (10명 교실에 3명만 있으면 슬랙=7) |
| O(1) | 데이터가 아무리 많아도 속도가 일정한 것. 전화번호부에서 이름으로 바로 찾기 |
| O(N) | 데이터가 N개면 최대 N번 봐야 하는 것. 출석부를 처음부터 끝까지 읽기 |

## 1. TArray의 메모리 할당 전략

### 핵심 멤버

```cpp
// Array.h
ElementAllocatorType AllocatorInstance;
int32 ArrayNum;   // 실제 원소 수 (Num())
int32 ArrayMax;   // 할당 용량 — 현재 공간에 최대 몇 개 들어가는지 (Max())
// 슬랙(여유) = ArrayMax - ArrayNum
```

> **왜 Num과 Max가 따로인가?**
> Add할 때마다 메모리를 늘리면 매번 재할당이 일어나서 느리다.
> 그래서 "넉넉하게" 확보해두고(Max), 실제 사용량(Num)만 따로 관리한다.

### 증가 정책 — 공간이 부족할 때 얼마나 늘리나?

```
[첫 번째 Add]
  → 4개분 공간 확보 (FirstGrow=4)

[후속 Add에서 공간 부족 시]
  → 새 용량 = 현재 수 × 1.375 + 16
  → 할당자 버킷 크기에 맞춰 올림 (QuantizeSize)
```

**예시 (int32 배열):**

| 시점 | 원소 수 | 계산 | 확보 용량 |
|------|---------|------|----------|
| 첫 Add | 1 | FirstGrow | ~4 |
| 5번째 | 5 | 5×1.375+16=22.9 | ~24 |
| 25번째 | 25 | 25×1.375+16=50.4 | ~52 |

> **왜 ×1.375인가?** (std::vector는 보통 ×2)
> ×2보다 메모리를 덜 쓰면서, QuantizeSize로 할당자 버킷에 맞추면 실질 성능은 비슷하다.

### 축소 정책 — 원소를 많이 삭제했을 때

```
축소 조건 (모두 충족해야 축소):
  ① 남은 여유 ≥ 16KB  또는  사용률 < 66.7%
  ② 여유 슬롯 > 64개  또는  배열이 완전히 빔
→ 조건 충족 시 현재 크기에 맞춰 재할당
→ 미충족 시 기존 용량 유지 (빈번한 재할당 방지)
```

### 주요 크기 조절 함수

| 함수 | 동작 | 비유 |
|------|------|------|
| `Reserve(N)` | N개 이상 공간 확보 (축소는 안 함) | "최소 N명 앉을 자리 준비해줘" |
| `Shrink()` | 여유 공간 제거 (딱 맞게) | "빈 의자 다 치워" |
| `Reset(N)` | 내용 삭제, 공간은 유지 | "학생 다 보내고, 교실은 그대로" |
| `Empty(Slack)` | 내용 삭제 + 공간도 조절 | "학생 보내고 교실도 줄여" |

### 할당자 종류

| 할당자 | 특징 | 비유 |
|--------|------|------|
| `FDefaultAllocator` | 힙 할당 (기본) | 필요할 때 교실 빌리기 |
| `TInlineAllocator<N>` | N개를 객체 내부에 저장, 초과 시 힙 | 내 책상에 N개까지 놓고, 넘치면 교실 빌리기 |
| `TFixedAllocator<N>` | N개 고정, 초과 불가 | 교실 크기 고정, 넘치면 에러 |

## 2. TSet의 내부 구조

### 구조 개요

> TSet은 "이 값이 있는가?"를 빠르게(O(1)) 확인하는 컨테이너.
> 내부적으로 **해시 테이블** + **TSparseArray** 조합.

```
TSet<T>
  ├─ Elements: TSparseArray   ← 실제 원소들이 연속 저장됨
  ├─ Hash: 버킷 배열[]         ← 해시값 → "어느 원소인지" 가리킴
  └─ HashSize: 버킷 수 (항상 2의 거듭제곱)
```

### 충돌 처리: 체인 해싱

> 같은 해시 버킷에 여러 원소가 배정되면, 원소끼리 "다음 원소" 포인터로 줄을 선다.

```
해시 버킷 배열:
  [0] → 원소3 → 원소7 → (끝)     ← 이 버킷에 2개 원소가 줄 섬
  [1] → (비어있음)
  [2] → 원소1 → (끝)
  [3] → 원소0 → 원소5 → (끝)

TSparseArray (원소 저장소):
  [0] {Value="A", 다음=5, 버킷=3}  ← 할당됨
  [1] {Value="B", 다음=없음, 버킷=2}
  [2] {비어있음 — 프리리스트}        ← 삭제된 슬롯, 재활용 대기
  [3] {Value="C", 다음=7, 버킷=0}
```

**장점**: 원소가 TSparseArray에 연속 저장 → 메모리 캐시 효율 우수 (std::unordered_set보다 빠름)

### 버킷 수 결정

| 원소 수 | 버킷 수 | 평균 체인 길이 |
|---------|---------|---------------|
| 1~3 | 1 | 1~3 |
| 4 | 16 | ~0.25 |
| 100 | 64 | ~1.6 |
| 1000 | 512 | ~2 |

로드 팩터(버킷당 평균 원소): 약 2. std::unordered_set(약 1)보다 높지만, 연속 메모리 장점으로 보상.

## 3. TSparseArray — TSet의 저장 백엔드

> "구멍 난 배열" — 중간에 빈 슬롯이 있어도 인덱스가 변하지 않는 배열

```
TSparseArray
  ├─ Data: TArray (원소 또는 프리리스트 링크)
  ├─ AllocationFlags: 비트 배열 (각 슬롯의 사용/미사용 표시)
  ├─ FirstFreeIndex: 첫 번째 빈 슬롯 번호
  └─ NumFreeIndices: 빈 슬롯 수
```

**비유**: 아파트 호수. 302호가 이사 가도 호수는 그대로(인덱스 안정). 다음 입주자가 302호에 들어감.

**추가**: 빈 슬롯이 있으면 거기에 넣음 → O(1)
**삭제**: 해당 슬롯을 "빈 목록"에 추가 → O(1), 다른 원소의 인덱스에 영향 없음

## 4. TMap의 해시 테이블 구현

> TMap은 내부적으로 **TSet<TPair<Key,Value>>** 하나로 구현됨. 매우 단순한 구조.

```
TMap<K, V>
  └─ TSet<TPair<K,V>> Pairs   ← 유일한 멤버
```

- `TPair<K,V>` = Key와 Value를 묶은 쌍
- 해시 함수: `GetTypeHash(Key)` — 키 타입별로 전역 오버로딩
- `TMap` = 키 중복 불가, `TMultiMap` = 키 중복 허용

### 주요 연산

| 함수 | 동작 | 속도 | 비유 |
|------|------|------|------|
| `Add(Key, Value)` | 키-값 쌍 추가 (기존 키면 덮어씀) | O(1) 평균 | 전화번호부에 등록 |
| `Find(Key)` | 키로 값 검색 → Value* 반환 | O(1) 평균 | 이름으로 전화번호 찾기 |
| `Remove(Key)` | 키-값 쌍 삭제 | O(1) 평균 | 전화번호부에서 삭제 |
| `Contains(Key)` | 키 존재 여부 | O(1) 평균 | "이 사람 번호 있어?" |
| `FindKey(Value)` | 값으로 키 역검색 | **O(N)** | 전화번호로 이름 찾기 — 처음부터 끝까지 뒤져야 함 |

## 5. 이터레이터 (순회 방법)

```cpp
// TArray — 가장 단순, 연속 메모리라 빠름
for (auto& Item : MyArray) { ... }

// TSet — 비트 배열로 빈 슬롯 건너뛰며 순회
for (auto& Item : MySet) { ... }

// TMap — Key/Value 쌍으로 순회
for (auto& Pair : MyMap) {
    Pair.Key;    // 키
    Pair.Value;  // 값
}
```

## 6. STL 컨테이너와의 핵심 차이점

### TArray vs std::vector

| 항목 | TArray | std::vector |
|------|--------|-------------|
| 증가 배율 | ×1.375 + 16 | 보통 ×2 |
| 자동 축소 | 조건부 축소 있음 | 없음 (shrink_to_fit 수동) |
| 인라인 저장 | `TInlineAllocator<N>` 지원 | 미지원 |
| O(1) 삭제 | `RemoveAtSwap()` 내장 | 직접 구현 |
| SizeType | `int32` (signed) | `size_t` (unsigned) |

> `RemoveAtSwap()`: 삭제할 원소에 마지막 원소를 덮어씌우고 크기를 줄임. **순서가 바뀌지만** O(1). 순서가 중요하지 않은 경우 매우 유용.

### TMap vs std::unordered_map

| 항목 | TMap | std::unordered_map |
|------|------|-------------------|
| 원소 저장 | **연속 메모리** (TSparseArray) | 노드별 개별 힙 할당 |
| 캐시 효율 | 좋음 (연속 저장) | 나쁨 (포인터 추적) |
| 삭제 | O(1), 인덱스 안정 | O(1), 이터레이터 무효화 |

> **핵심 차이**: TMap/TSet은 원소를 연속 메모리(TSparseArray)에 저장하여 캐시 효율이 좋다.
> std::unordered_map은 각 원소를 별도 힙에 할당하여 메모리가 흩어진다.
