## 1. 메모리 관리 패턴 — DX11 소규모 엔진에 적용할 만한 것

### 1.1 현재 프레임워크의 메모리 구조

```
CBase (m_iRefCnt)
├── CGameObject (Device/Context/GameInstance AddRef)
│   └── CTransform* (Safe_Release)
├── CComponent (Device/Context AddRef)
├── CLayer (list<CGameObject*> Safe_Release)
└── 각 Manager (Safe_Release로 정리)
```

- **할당**: `new` (시스템 malloc)
- **해제**: CBase::Release() → refcnt 0 → Free() → `delete this`
- **소유 추적**: Safe_AddRef / Safe_Release 쌍

### 1.2 UE4에서 가져올 만한 패턴

#### [적용 권장] A. 디버그 할당자 프록시

UE4의 `FMallocPoisonProxy`처럼 해제된 메모리를 특정 값(0xCD)으로 채워 use-after-free를 조기 감지하는 패턴.

```cpp
// 디버그 빌드 전용 — Release()에서 Free() 호출 후, delete 직전에 삽입
// 주의: vtable 포인터도 덮어쓰므로 반드시 Free()(가상 함수) 호출 이후에 실행
_uint CBase::Release() {
    if (0 == m_iRefCnt) {
        Free();                                // 가상 함수 — vtable 필요
#ifdef _DEBUG
        memset(this, 0xCD, sizeof(*this));     // vtable 포함 모두 오염
#endif
        delete this;                           // operator delete만 호출 (소멸자는 trivial)
        return 0;
    }
    else { return m_iRefCnt--; }
}
```

**적용 이유**: 현재 프레임워크는 Safe_Release 반환값이 0일 때만 포인터를 nullptr로 설정하므로, AddRef 짝이 안 맞으면 이미 삭제된 객체에 접근할 수 있다. 0xCD 패턴으로 채우면 멤버 변수 읽기 시 즉시 이상값 감지 가능.

**주의**: `memset` 후 `delete this`에서 소멸자가 호출되면 오염된 vtable 참조로 크래시. 현재 프레임워크는 `virtual ~CBase() = default`이고 Free()에서 정리를 완료하므로, 소멸자에서 추가 가상 호출이 없어 안전. 단, 파생 클래스에 비-trivial 소멸자를 추가하면 문제가 되므로, 이 패턴은 **Free() 패턴을 엄격히 유지하는 전제** 하에서만 적용.

**비용**: 디버그 빌드 한정이므로 릴리즈 성능 영향 없음.

#### [적용 권장] B. Pool Allocator (소형 객체 전용)

UE4 FMallocBinned2의 핵심 아이디어를 소규모로 적용:

```cpp
// 고정 크기 풀 — Component처럼 자주 생성/삭제되는 소형 객체에 적합
template<typename T, size_t BlockCount = 64>
class TObjectPool {
    union Block { T obj; Block* next; };
    Block  m_Storage[BlockCount];
    Block* m_FreeHead;
public:
    T* Allocate()   { /* FreeHead에서 꺼내기 */ }
    void Deallocate(T* p) { /* FreeHead에 반환 */ }
};
```

**적용 시기**: 총알, 이펙트, AI 상태 등 동일 타입 객체가 매 프레임 수십 개 생성/삭제될 때. 현재 프레임워크 규모에서는 시기상조이나, **구조만 인지**해두고 병목이 확인되면 도입.

**비용**: 구현 ~50줄, 풀 크기분 메모리 상시 점유.

#### [시기상조] C. FMallocBinned2 스타일 전역 할당자 교체

프레임워크가 DX11 학습 목적이므로, 커스텀 전역 할당자는 과잉 설계. OS malloc 또는 mimalloc 링크로 충분.

**결론**: 전역 할당자 교체보다 **디버그 프록시(A)** + **필요 시 오브젝트 풀(B)** 조합이 현실적.

### 1.3 스마트 포인터 관련

현재 프레임워크는 CBase::Release() 수동 호출 방식. UE4의 TSharedPtr 같은 자동 관리를 부분 도입하면:

| 패턴 | 현재 방식 | UE4 TSharedPtr 스타일 | 권장 |
|------|-----------|----------------------|------|
| Device/Context 참조 | Safe_AddRef/Release 수동 | ComPtr<ID3D11Device> | **ComPtr 즉시 적용 가능** |
| GameObject 간 참조 | Safe_AddRef/Release 수동 | TWeakPtr 스타일 | 현재 유지 (아래 4절 참고) |

`ComPtr<T>`는 DirectX COM 객체 전용 스마트 포인터로, UE4의 TSharedPtr보다 프레임워크에 적합:

```cpp
// 현재
ID3D11Device* m_pDevice = { nullptr };
Safe_AddRef(m_pDevice); // 생성자
Safe_Release(m_pDevice); // Free

// ComPtr 적용 시
Microsoft::WRL::ComPtr<ID3D11Device> m_pDevice;
// AddRef/Release 자동 관리, Free()에서 별도 해제 불필요
```

**전환 비용 주의**: ComPtr 도입 시 단순 교체가 아님:
- CComponent/CGameObject의 복사 생성자에서 `Safe_AddRef(m_pDevice)` 제거 필요
- Free()에서 `Safe_Release(m_pDevice/m_pContext)` 제거 필요
- 모든 파생 클래스(CVIBuffer, CTransform 등)도 동일 수정
- 프레임워크 전체의 Device/Context 전달 패턴이 변경됨

**판단**: 학습 목적 프레임워크에서는 CBase 체계의 일관성 유지가 우선. ComPtr은 **새 프로젝트 시작 시** 또는 **Graphic_Device 클래스 한정**으로 도입하는 것이 현실적. 기존 CBase 계열에 부분 적용하면 두 가지 메모리 관리 방식이 혼재되어 혼란 야기.

## 2. 델리게이트 — 프레임워크 구현과 UE4의 구조적 차이

### 2.1 현재 프레임워크 상태

CONTEXT.md에 "델리게이트 기반 이벤트 시스템" 기술 예정으로 명시되어 있으나, 현재 소스에는 아직 구현되지 않음. 이벤트 전달은 직접 함수 호출 방식:

```
CLevel_Manager::Change_Level() → CGameInstance::Clear_Resources()
CLayer::Priority_Update() → CGameObject::Priority_Update()
```

### 2.2 프레임워크에 델리게이트를 구현한다면 — UE4와의 구조적 차이

| 설계 결정 | UE4 | 프레임워크 권장 |
|-----------|-----|----------------|
| 바인딩 타입 | Raw/SP/UObject/UFunction/Lambda 5종 | **Raw + Lambda** 2종 |
| UObject 연동 | WeakObjectPtr 유효성 검사 | 불필요 (GC 없음) |
| 블루프린트 | Dynamic Delegate (리플렉션) | 불필요 |
| 메모리 할당 | 힙 할당 기본 (인라인 옵션) | **인라인 16바이트 권장** |
| 멀티캐스트 안전성 | Lock-Compact (역순 순회) | 동일 패턴 권장 |
| 매크로 코드 생성 | DECLARE_DELEGATE (0~9 파라미터) | **std::function + 템플릿** |

### 2.3 최소 구현 제안

UE4 델리게이트의 핵심 패턴만 추출한 경량 버전:

**싱글캐스트:**
```cpp
template<typename Signature>
class TDelegate; // std::function 래퍼 + 바인딩 여부 확인
```

**멀티캐스트 (UE4의 Lock-Compact 패턴 적용):**
```cpp
template<typename... Args>
class TMulticastDelegate {
    vector<function<void(Args...)>> m_Listeners;
    bool m_bBroadcasting = false;
    // Broadcast 중 Remove → 즉시 삭제 대신 nullptr 마킹
    // Broadcast 끝 → Compact (nullptr 제거)
};
```

**UE4에서 반드시 참고할 것:**
1. **역순 Broadcast**: 실행 중 Add된 리스너가 이번 Broadcast에서 호출되지 않도록
2. **FDelegateHandle**: 등록 시 고유 핸들 반환, Remove 시 핸들로 제거 (포인터 비교 불필요)
3. **Payload(커링)**: `std::bind`나 람다 캡처로 대체 가능 — 별도 구현 불필요

**UE4에서 가져오지 않을 것:**
- DECLARE_DELEGATE 매크로 (C++17 variadic template으로 대체)
- UObject/UFunction 바인딩 (리플렉션 시스템 없음)
- Type Erasure 기반 다형 저장 (std::function이 이미 제공)

## 3. TArray 메모리 증가 정책 vs std::vector — Trade-off

### 3.1 수치 비교

| 항목 | TArray | std::vector (MSVC) |
|------|--------|--------------------|
| **증가 배율** | ×1.375 + 16 | ×1.5 |
| **첫 할당** | 4개 (FirstGrow) | 1개 |
| **자동 축소** | 조건부 (사용률 < 66.7%) | 없음 |
| **O(1) 삭제** | `RemoveAtSwap()` 내장 | 직접 구현 |
| **인라인 저장** | `TInlineAllocator<N>` | 없음 |
| **SizeType** | `int32` (signed) | `size_t` (unsigned) |

### 3.2 프레임워크 적용 시 판단

**std::vector 그대로 사용하되, UE4 패턴을 선택적으로 차용:**

| UE4 패턴 | 프레임워크 적용 | 방법 |
|----------|----------------|------|
| RemoveAtSwap | **적용 권장** | 유틸 함수로 구현 |
| 조건부 축소 | 불필요 | 벡터 규모가 작음 |
| 인라인 저장 | 선택적 | `boost::small_vector` 또는 자체 구현 |
| signed SizeType | 불필요 | MSVC 경고 무시 수준 |

**RemoveAtSwap 유틸:**
```cpp
template<typename T>
void RemoveAtSwap(vector<T>& v, size_t index) {
    v[index] = std::move(v.back());
    v.pop_back();
}
```

순서가 중요하지 않은 오브젝트 목록(Layer의 CGameObject 리스트 등)에서 O(N) → O(1) 삭제. 현재 `list<CGameObject*>`를 사용하는 Layer에서, 순회 성능이 중요해지면 `vector` + `RemoveAtSwap`으로 전환하는 것이 캐시 효율적.

### 3.3 list vs vector 선택 기준

현재 Layer는 `list<CGameObject*>` 사용:

| 기준 | list | vector |
|------|------|--------|
| 중간 삽입/삭제 | O(1) | O(N) 또는 O(1) Swap |
| 순회 | 느림 (포인터 추적) | **빠름 (연속 메모리)** |
| 메모리 | 노드당 2포인터 오버헤드 | 없음 |
| 이터레이터 안정 | 유지 | 무효화 |

**판단**: 게임 오브젝트 순회(Tick)가 매 프레임 발생하므로, 오브젝트 수가 수백 개를 넘으면 `vector` + `RemoveAtSwap`이 캐시 효율 면에서 유리. 현재 규모에서는 list도 문제없으나, TArray(=vector)가 UE4에서도 기본 컨테이너인 이유가 여기에 있다.

## 4. 참조 카운팅 구조 — UE4 관점 개선 제안

### 4.1 현재 프레임워크의 참조 카운팅 체계

```cpp
// CBase
_uint m_iRefCnt = {};  // 0에서 시작

_uint AddRef()  { return ++m_iRefCnt; }
_uint Release() {
    if (0 == m_iRefCnt) { Free(); delete this; return 0; }
    else { return m_iRefCnt--; }  // 후위 감소
}

// Safe_Release (Engine_Function.h)
template<typename T>
unsigned int Safe_Release(T& Instance) {
    unsigned int iRefCnt = { 0 };
    if (nullptr != Instance) {
        iRefCnt = Instance->Release();
        if (0 == iRefCnt) Instance = nullptr;
    }
    return iRefCnt;
}
```

**특성** (O09 분석에서 확인):
- refcnt 0에서 시작, 0인 상태에서 Release → 파괴 (COM과 다른 체계)
- 후위 감소는 의도적 — Safe_Release의 nullptr 설정과 정합

### 4.2 UE4의 참조 관리 방식과 비교

| 항목 | 프레임워크 | UE4 TSharedPtr | UE4 UObject |
|------|-----------|---------------|-------------|
| **카운트 시작** | 0 | 1 (생성 시) | GC 관리 |
| **해제 조건** | refcnt==0에서 Release | refcnt 1→0 | Mark-Sweep |
| **스레드 안전** | 없음 | ESPMode 선택 | GC 스레드 |
| **순환 참조 방지** | 수동 주의 | TWeakPtr | GC가 해결 |
| **null 안전** | Safe_Release 유틸 | TSharedRef (비-nullable) | - |

### 4.3 구체적 개선 제안

#### [권장 1] AddRef/Release 짝 누락 감지 — 디버그 빌드

가장 흔한 버그: AddRef는 했는데 Release를 빠뜨려 메모리 누수, 또는 그 반대.

```cpp
// Base.h — 디버그 빌드 전용
#ifdef _DEBUG
class CBase {
    _uint m_iRefCnt = {};
    const char* m_DebugClassName = nullptr;  // 클래스명 추적
    static std::atomic<int> s_LiveObjectCount;  // 살아있는 객체 수
public:
    CBase() { ++s_LiveObjectCount; }
    // Release에서 파괴 시 --s_LiveObjectCount
    static int GetLiveObjectCount() { return s_LiveObjectCount; }
};
#endif
```

**효과**: 프레임 끝에 `GetLiveObjectCount()`가 증가 추세이면 누수 의심. UE4도 `FPlatformMemory::GetStats()`로 유사하게 추적.

#### [권장 2] 순환 참조 명시적 문서화

현재 O12에서 지적된 순환 의존:
```
CGameInstance ──소유──→ CObject_Manager
CObject_Manager ──참조──→ CGameInstance (AddRef)
```

UE4 방식: TWeakPtr로 역참조를 약한 참조로 변경하면 순환이 깨짐. 프레임워크에서는 Release_Engine()의 명시적 해제 순서로 해결하고 있으므로, **UE4의 약한 참조 개념을 주석으로 문서화**하는 것이 현실적:

```cpp
// Object_Manager.h
// m_pGameInstance는 소유자를 역참조하는 "약한 참조" 개념
// Release_Engine()에서 명시적 순서로 해제되므로 순환 참조 안전
// UE4에서는 TWeakPtr로 구현하나, 현재 체계에서는 수동 관리
```

#### [참고] UE4 TSharedRef 아이디어

UE4의 `TSharedRef<T>`는 nullptr이 될 수 없는 스마트 포인터. API 설계 시 "이 인자는 절대 null이 아닌 유효한 객체"를 타입 수준에서 보장.

프레임워크에서는 Create() 패턴의 반환값이 항상 valid하므로, 추가적인 non-null 래퍼는 과잉. 다만 **향후 컴포넌트 시스템이 복잡해질 때** 이 개념을 인지하면 도움됨.

#### [시기상조] 스레드 안전 참조 카운팅

현재 프레임워크는 사실상 싱글 스레드 (로딩 스레드만 예외). UE4처럼 `std::atomic<int32>` 기반 스레드 안전 카운팅은 불필요. 멀티스레드 렌더링 도입 시 재검토.

## 5. 수학 라이브러리 — [1-5]에서의 적용 인사이트

### 5.1 현재 프레임워크 상태

Engine_Typedef.h에서 DirectXMath 타입을 직접 사용:
```cpp
typedef XMFLOAT4X4  _float4x4;
typedef XMVECTOR    _vector;
typedef XMMATRIX    _matrix;
```

CTransform에서 `_float4x4 m_WorldMatrix`로 행렬 저장, `XMLoadFloat4`/`XMStoreFloat4`로 SIMD 변환.

### 5.2 UE4 패턴과의 대응 — 이미 적절한 부분

| UE4 | 프레임워크 | 평가 |
|-----|-----------|------|
| FVector/FMatrix (자체 래퍼) | XMFLOAT3/_float4x4 (DirectXMath 직접) | **적절** — 소규모 엔진에서 자체 래퍼는 과잉 |
| VectorRegister (SIMD 추상화) | XMVECTOR (DirectXMath SIMD) | **적절** — [1-5]에서도 DirectXMath 직접 사용 권장 |
| 행 벡터 × 행렬 규약 | HLSL `mul(v, M)` 호환 | **적절** |

### 5.3 추가 적용 검토 항목

**Reversed-Z 투영** ([1-5]에서 강력 권장):
- 현재 프레임워크에 투영 행렬 설정 코드가 아직 없음 (Graphic_Device에서 뷰포트만 설정)
- 향후 카메라/투영 시스템 구현 시 [1-5]의 Reversed-Z 섹션 참고
- 핵심: `D3D11_COMPARISON_GREATER_EQUAL` + `D32_FLOAT` 깊이 포맷

**Transform 컴포넌트의 SIMD 활용**:
- 현재 CTransform은 `_float4x4`(비-SIMD)로 저장 후 필요 시 `XMLoadFloat4x4`로 변환
- UE4의 TransformVectorized처럼 상시 SIMD(`XMMATRIX`)로 유지하면 행렬 연산 시 Load/Store 비용 제거
- 단, 정렬 제약(16바이트) 때문에 `new`로 할당 시 주의 필요 → 현재 단계에서는 현행 유지가 안전

## 6. 문자열 식별자 — [1-6]에서의 적용 인사이트

### 6.1 현재 프레임워크의 문자열 사용

프로토타입/레이어 키로 `_wstring`(=`std::wstring`) 사용:
```cpp
// Prototype_Manager
map<_wstring, CBase*> PROTOTYPES;
// Object_Manager
unordered_map<_wstring, CLayer*> LAYERS;
```

`Add_Prototype(iLevelIndex, L"Prototype_BackGround", ...)`처럼 문자열 리터럴로 키 지정.

### 6.2 UE4 FName 패턴 적용 가능성

| 항목 | 현재 (wstring 키) | FName 스타일 (해시 키) |
|------|-------------------|----------------------|
| 검색 | O(N) map / O(1) unordered_map | O(1) 정수 비교 |
| 메모리 | 키마다 wstring 복사 | 4바이트 ID |
| 디버깅 | 문자열 그대로 확인 가능 | 역방향 테이블 필요 |

**적용 판단**:
- 현재 프로토타입/레이어 수가 수십 개 수준이므로 wstring 키의 성능 문제 없음
- `unordered_map`은 이미 해시 기반이므로 검색은 O(1) 평균
- FName 스타일 전환의 실질적 이득이 적음

**단, 향후 적용이 유효한 경우**:
- AI 상태 머신에서 상태 이름을 매 프레임 비교할 때 → [1-6]의 "옵션 A: 해시만 사용" 패턴
- 에셋 경로가 수천 개로 늘어날 때 → wstring 비교 비용이 무시 못할 수준

```cpp
// [1-6] 옵션 A 적용 예시 — AI 상태 식별자
constexpr uint32_t STATE_IDLE   = CompileTimeHash("Idle");
constexpr uint32_t STATE_ATTACK = CompileTimeHash("Attack");
// 매 프레임 비교: 정수 비교 O(1), wstring 비교 대비 수십 배 빠름
```
